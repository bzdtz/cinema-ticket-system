### 403 那两条的判定依据（一次讲清，省得来回猜）

`commons/src/main/resources/com/saodi/mapper/PermissionMapper.xml` 里权限判定只有一句：

```sql
SELECT count(*) b FROM role_permission
JOIN permission ON role_permission.permission_id = permission.id
JOIN cinema_user ON cinema_user.role = role_permission.role_id
WHERE cinema_user.account = #{account}
  AND (#{url} = permission.url OR #{url} LIKE CONCAT(permission.url,'/%'))
```

匹配不到就 `count=0` → `LoginInterceptor.java:74` 回 `code:510 权限不足` → `main.js:59` `router.push({name:'403'})`。
注意用的是 `permission.url,'/%'`（带斜杠），所以 `/movie` 这条权限**盖不住** `/movie-cinema-mapping/update/5`，
而库里根本没有 `/movie-cinema-mapping` 这一行 —— 两个角色都进不去。
顺带一提：`Check` 里是 `JOIN cinema_user ON cinema_user.role = role_permission.role_id`，所以 `role` 为 NULL 的管理员永远 count=0 → 干什么都 403。
实测 account=10077（id=6）的 `role` 就是 NULL（它同时 `status=0`，登录回 504 该账号被禁用，所以这条暂时踩不到，但把 status 打开就是）。13 个管理员里只有 10 个启用：**5 个 1001 + 5 个 1002**，另外 2 个 1001 被禁用、1 个无角色被禁用。也就是说「点排片表进 403」现在影响的是 5 个能登录的账号。

## 三、我推翻掉的误报（别照着这些改）

这几条是我让子代理扫出来的，逐条验过之后**不成立或不是你的问题**：

- **`/business`、`/food`、`/up`、`/userInfo/update`、`/app/user/register` 后端没有 handler** —— 事实成立（我把 78 个 handler 和 77 个前端 URL 字面量做了 diff，这 13 条确实对不上），但**入口全都不可达**：侧边栏是 `menu` 表驱动的（`Sidebar.vue:178` 请 `/menu/roleMenu/{role}`），菜单里只有 9 个分组——用户/电影/影院/影厅/电影排片/评论/订单/个人/系统管理，商家表、餐品表、上传插件、`/userInfo` 这几个模板页面压根不在里面；`Order.vue` 里那个 `/business/batch` 整段是注释掉的（365-373 行）；admin `Login.vue` 的 `logUp()` 没有任何按钮绑定（模板里只有一个「登录」按钮）。这些是 vue-manage-system 模板残留。
- **「影评/想看表结构漂移：`movie_comment` 没有 `content` 列、`id` 没有自增」** —— 那是 `all.sql` 的状态。**当前 `theater` 库 `DESCRIBE movie_comment` 有 `content`/`score`，两张表都有 `auto_increment`**。这条如果不纠正，会害得你去改已经好好的功能。
- **`userdata.vue:105` 读 `$route.params.account` 所以个人信息页坏** —— 第 106-111 行紧跟着 `else { str = JSON.parse(localStorage.getItem("loginUser")).account }` 兜底，正常。
- **`RoleMenu.vue:68` / `RolePermission.vue:59` 读 `$route.params.id` 但路由没 `:id` 所以完全打不开** —— 我用项目自带的 `vue-router 4.0.4` 在 node 里跑了最小复现：`{name:'roleMenu', params:{id:'55'}}` → `currentRoute.params = {"id":"55"}`，`fullPath = /roleMenu`。**命名路由 push 的未声明 params 会保留**，所以从角色管理点进去是能用的，**只有 F5 刷新才会丢 params** 被弹回 `/roletable`。准确说法是"不能刷新/不能收藏/不能直接发链接"，不是"打不开"。
- **`PermissionTable.vue` 用 `e.status==200` 判断所以永远失败** —— 对 axios 来说 `e.status` 就是 HTTP 状态码，写法本身没错。真正的问题是**它察觉不到业务失败**（后端返回 `code:505` 时 HTTP 仍是 200，界面照样弹"成功"）。这是另一码事，别按原诊断改。
- **app 侧 `/cinema/**` 被放行所以前台能改影院** —— `app/.../CinemaController.java` 只有 `/list`、`/get/{city}`、`/getCinema`、`/getByid/{id}` 四个读方法，没有写接口。漏洞只在 manager 那一侧（见 P0 第 1 条）。
- **用户端接口大面积 404** —— 前台 36 个 `/app/...` URL 我逐个对过 46 个 handler，**全部存在**。前台的问题从来不是接口缺失。

### ⓪ 先报一条审计当时没抓到的、而且级别最高的

**`spring.redis.password` 和本机 Redis 对不上 —— 这不是"某个功能坏了"，是后台全军覆没 + 用户端后端起不来。**

本机 redis 的 `requirepass` 是空的（`redis-cli CONFIG GET requirepass` 返回空，`redis.windows.conf:503` 那行本来就注释着），
而 `manager/application.yml` 和 `app/application.yml` 都写死了 `password: 123456`。Lettuce 照样发 `AUTH`，Redis 回：

```
io.lettuce.core.RedisCommandExecutionException: ERR Client sent AUTH, but no password is set
```

两个后果，都不是同一回事：

- **manager**：`LoginInterceptor.java` 里那句 `redisTemplate.opsForValue().get(token)` 冒泡成 **HTTP 500**，
  于是**只要带 token 的请求全部"服务器内部错误"**。审计里第 7 条我归因给"`main.js` 没 `localStorage.clear()` 所以来回弹登录页"——
  那个是真，但**当时你在后台看到"每个菜单都点不动"的直接原因是这个 500**，不是会话过期。这一条要纠正。
- **app**：`app/config/RedisConfig.java:14` 有个 `RedisMessageListenerContainer`（监听 `__keyevent@0__:expired` 用来超时释放未支付票），
  它在容器启动阶段就要连 Redis → **`Application run failed`，:81 根本起不来**。我 12:59 重启它的时候复现了：
  启动 43 秒后 `listenerContainer` 启动失败，进程退出码 1。之前那次能跑，是因为老进程的连接是在 Redis 改回无密码**之前**建立的，
  Lettuce 不会每条命令重新 AUTH，所以一直没露馅——直到进程重启。

改法（两处 yml 同一行）：`password: ${REDIS_PASSWORD:}` —— 默认不带密码，跟本机实际一致；哪天给 Redis 设了口令，
`set REDIS_PASSWORD=xxx` 就行，不用再改文件。同时给拦截器和登录接口包了兜底：
**Redis 读失败 = 按未登录处理（501，前端跳登录页）**，**写失败 = `ERROR(517,"会话存储(Redis)不可用…")`**，都不再是裸 500。

实测（重启后）：

| 打的是哪个 | 修复前 | 修复后 |
|---|---|---|
| `POST /cinema/getByPage` + 任意假 token | `{"code":500,"msg":"服务器内部错误"}` | `{"code":501,"msg":"登录验证失败"}`，日志 `登录拦截：token=有，会话命中=false` |
| app 进程能不能起来 | `Started` 之后再无日志，`BUILD FAILURE`，81 不监听 | `Started AppStart in 43.245 seconds`，`TCP 0.0.0.0:81 LISTENING` |
| 两边日志里的 Redis 异常计数 | 一堆 | `grep -c "RedisConnectionException"` 加上 `grep -c "Client sent AUTH"` = **0** |

### ① 七牛 AK/SK：源码里已经拿走，控制台那把 key 顺手禁用即可

`grep -rn "accessKey=\"" --include=*.java` 现在是 **0 命中**。

四项配置默认**空**（`access-key: ${QINIU_ACCESS_KEY:}` 这种写法），所以未配置时点上传会直接得到

### 为什么跑在浏览器里

## 十二、外部热度榜：快照表 + 第 6 个工具（2026-10-10）

### 要解决的是数据陈旧，不是查询能力

「最近什么在映、谁最热」以前只能靠 `list_movies` 回答，而 `movie.want_number`/`score` 是 2024-02 那次入库存的，`release_time` 最晚停在 2024-02-08，库里最早的排片是 2023-12-31。模型拿这份数答「最近」，报出去的是一串两年前的数字加上一个「今天」的语气 —— 比答「查不到」更坏，因为用户没地方怀疑。

### 源是探测过的，不是猜的

同一天用 curl 打过四个：豆瓣 `j/search_subjects`（**必须带 `Referer: https://movie.douban.com/`**，只带 UA 回 400）免 key 可用，给片名/评分/封面/subject id/url；豆瓣条目详情页 302；猫眼票房接口要 `signKey`，403；TMDB 可达但要 key（401）。所以选了 `search_subjects`，代价是**拿不到票房**，页面上那块因此叫「外部热度榜」而不是继续挂「前10票房」的名字。

### 形态：抓 → 落快照表 → 只读

`sql/movie-hot-snapshot-2026-10-10.sql` 建 `movie_hot_snapshot`（28 张表里的第 28 张）。一批一次抓取，`batch_id` 到毫秒（只到秒的话同一秒点两次会撞 `uk_batch_rank`），留最近 10 批 —— 这是缓存不是档案，留批次是为了能回答「这份榜单是什么时候抓的」，并且抓失败时旧批次原样还在。

- 定位最近一批靠 `ORDER BY id DESC LIMIT 1`，不靠 `fetched_at`：同一秒抓完的两批会并列。

- `RuleAssistant.hot()` 注入的是**同一个 `HotNowTool` bean**，兜底路径和模型路径读同一份数，延续「兜底引擎不是降落页，是同一批工具的第二个驱动端」这条。

### promote 是点出来的，不是自动的

榜单前几部里站内没有的，`POST /app/hot/promote?limit=5` 才补成影片并排场次。这一步单独一个动作，因为它动的是 `movie` 和 `showtimes` 两张卖票用的表，而外部日榜天天变。实测结果：`movie` 多了 id 59-63（功夫女足/一个部门的诞生/庆州纪行/潜伏6/罗斯），`showtimes` 多了 id 33-57 共 24 场，日期 2026-10-10..10-18，只落在影院 1（新乡万达 IMAX）和 2（辉县）。于是 **影院 1 从 16 场变 32 场，影院 2 从 3 场变 11 场**，安阳万达（10410）维持 2 场，全场 21 → 45。

新场次的座位矩阵是抄同厅模板场次翻出来的：已售→可选，认不出的脏值→ -2 损坏。探针核过新行 `free=100 / unknown=0`，`SeatMatrix.serialize` 不会把 `VALUE_UNKNOWN`（`Integer.MIN_VALUE`）原样拼进字符串 —— 那比 `"p30"` 更坏。模板特意避开场次 12/19/21，就是躲开那三行的历史脏值。

补进来的片只有榜单真给的片名/评分/海报，时长、地区、上映日期、想看数**留 NULL 不编**，所以它们的详情页看着比老片空。

### 首页跟着改了两处

- 右侧「前10票房」是写死在 `data()` 里的数组（2023 年贴进去的演示值），TOP100 也只剩一个写死条目，两块一起换成：外部热度榜（带来源与抓取时间，榜首用大图卡）+ 站内评分榜（直接从热映结果里排）。两个一次性的动作按在册表面上：抓取中只做灰字，不禁用入口；点没进库的那行不跳转，只说一句「站内还没有这部片」。
- 「正在热映」原来是 `WHERE CURRENT_TIMESTAMP > release_time ORDER BY box_office` —— 新补的片 `release_time` 是 NULL，NULL 参加任何比较都是 unknown，于是它们**两个板块都进不去**，首页上根本看不见。改成优先按本站未来真排着的场次数排，没场的再退回票房；「即将上映」（`release_time > now`）不动，两边不会重。同一条 SQL 直接在库里跑过：前 5 是补进来的片（upcoming 6/5/5/4/4），后面 3 个位置还是老片。
- 顺手一处崩溃：模板里 `movie.tag.tag`，补进来的片没有 `tag_movie` 关系，`tag` 为 null 会让整个热映板块渲染报错。改成 `v-if="movie.tag"`，评分为空显示「暂无评分」。

### 评测口径同一天跟上（30 → 33 条）

新增 `A6 最近热度榜上最热的是哪部`、`A7 最近大家都爱看什么`（这两条都 `need: hot_now`，且 A7 的 `mustNot` 把那个旧想看数 `1450254`/`145万` 钉死）、`C7 2026-10-17 有哪些场次`（库里第一次有往后的排片，答得出来说明它真按 `date` 筛了）。改口径的三条：`A1` 从 `need: list_movies` 放宽成 `any: [list_movies, hot_now]`（守规则 9 的答复在旧口径下反而不过）、`B3/C3` 的 16 → 32、`B4` 的「今晚」现在有真场了所以两条真话都认。`C6` 的截断前提在 45 行下仍然成立：场次 27 还是第 21 条，新加的 2026 那一周全排在它后面。
判分器自己那处也改了写法：热度榜上的片名不写死在 harness 里（写死就又攒一份会过期的榜单），改成开跑前从 `/app/hot/list` 现读当前批次，`A6/A7` 用「答案里得出现役快照上的片名」做事实核对；读不到快照时对走过 `hot_now` 的答案免检，别的用例照旧。

### 验到哪一步

`refresh()/current()/promote()` 用临时 `ApplicationRunner` 探针在无登录态下端到端跑过并删掉了探针与 `target/classes` 里的 `.class`；`MovieMapper.xml` 由 MyBatis 在启动时解析（`:81` 起来了就说明没写坏），那条 SQL 也在库里直接跑过。**首页那块和 33 条的全量读数还没验** —— `:81` 重启会把他登出，这两件都要他的新会话。
